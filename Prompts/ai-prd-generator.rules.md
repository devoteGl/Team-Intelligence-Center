# AI-PRD 生成规则

## 用途

为新产品、重大用户旅程或需要长期维护的产品行为生成可确认、可验收的 PRD。
本文是 `prd-author` 的详细写作参考，不是所有开发任务的默认模板。

PRD 定义产品为什么存在、服务谁、用户如何完成目标以及什么结果才算完成。
它不替代技术设计、API 契约、数据库 Schema、任务计划或测试证据。

## 适用边界

使用本文：

- 从零建设产品或新的业务域；
- 改变主要角色、核心用户旅程或产品边界；
- 多个独立消费者需要长期共享同一产品事实。

不使用本文：

- 不改变用户可见行为的 Bug、重构或依赖升级；
- 已确认 PRD 下的纯实现任务；
- 开发完成后的事实同步，此时使用 `post-dev-prd-sync`；
- 老系统事实还原，此时先区分代码事实、文档事实和待确认推断。

## 产品基线

确认以下事实前，PRD 保持 `DRAFT`：

```yaml
product_baseline:
  owner: "有权确认产品方向的人"
  users: []
  outcome: "用户最终得到的可观察结果"
  primary_journey: []
  scope: []
  non_goals: []
  success_criteria: []
  evidence: []
  open_decisions: []
```

只有会导致明显不同产品结果的未知项才询问用户。能从正式资料、真实界面、运行时
或只读调查确认的内容先取证；无法确认的内容明确标为待决，不用“最佳实践”补齐。

## 写作流程

1. 识别 PRD owner、消费者、已有事实源和当前状态。
2. 汇总用户输入、业务材料、现有 PRD、真实产品行为和已确认决策；事实、候选和
   冲突分别记录。
3. 形成产品基线，先解决会改变目标、范围、主旅程或验收的决策。
4. 若产品包含界面，明确角色、用户旅程、信息架构、界面状态和关键交互；视觉稿可由
   专门设计能力承载，PRD 只引用其确认结果。
5. 把重要行为写成可观察验收标准，覆盖正常、空、加载、失败、无权限和恢复路径中
   与当前产品有关的部分。
6. 按需求形状选择章节，输出 PRD 草稿；不为凑模板生成空章节。
7. 交付草稿前自查基线、可验收性、一致性和范围扩张；产品 owner 要求独立
   审查或准备确认基线时，再单独使用 `prd-review-checklist`。
8. 只有有权 owner 明确确认后，才把状态从 `DRAFT` 改为 `CONFIRMED`。

## 推荐结构

按需求形状选择章节；以下是可组合结构，不要求全部出现：

```markdown
# <产品或能力名称> PRD

状态：DRAFT
Owner：<待确认或姓名/角色>

## 产品背景与目标
## 用户与职责
## 当前范围与非目标
## 核心用户旅程
## 功能行为与业务规则
## 页面、信息架构与界面状态
## 数据需求与隐私边界
## 验收标准
## 证据、假设、冲突与开放问题
## 版本与替代关系
```

### 产品目标

- 用用户结果描述，不用模块、表或接口数量替代。
- 每个目标给出验证方式；无法量化时使用可观察行为。
- 非目标必须足以阻止已知范围蔓延。

### 用户旅程

- 写清起点、用户动作、系统响应、终点和失败恢复。
- 区分日常用户、配置者、复核者和管理员；技术对象不自动成为用户步骤。
- 多条旅程只保留真正独立的用户目标，不按后端模块拆分。

### 页面与界面状态

对用户可见产品，按需要覆盖：

- 页面/视图的职责和入口；
- 默认、空、加载、成功、失败、无权限和阻断状态；
- 用户动作后的反馈、下一步和恢复；
- 桌面、移动、键盘或辅助技术要求，仅在真实用户和平台需要时声明。

PRD 描述业务所需数据和展示语义，不提前冻结 API 路径、请求结构、数据库字段或
框架。跨实现边界的精确结构由 OpenSpec、SDD 或契约承载。

### 验收标准

每条关键需求至少有一种可执行或可观察证明：

```text
给定真实角色和前置事实
当用户或系统执行目标动作
那么出现明确结果，并且禁止的副作用没有发生
```

验收同时声明数据范围、环境、身份、失败关闭和清理边界。静态检查、构建通过或
fixture 结果不能替代要求真实用户旅程的验收。

## 证据与状态

关键声明使用以下状态之一：

- `CONFIRMED`：由有权 owner 明确确认；
- `EVIDENCED`：由可靠资料或运行时证据支持，但尚未形成产品决定；
- `CANDIDATE`：合理候选，等待确认；
- `CONFLICT`：来源互相矛盾；
- `UNKNOWN`：证据不足。

PRD 整体状态使用 `DRAFT`、`REVIEW`、`CONFIRMED` 或 `SUPERSEDED`。实现完成、测试
通过或代码已发布都不能自动把 PRD 转为 `CONFIRMED`。

## 技术探针边界

PRD 确认前可以做可逆技术探针，用于验证可行性、性能或外部依赖。探针必须标明
假设、清理方式和不能证明的内容；它不能冻结正式 API、Schema、菜单、领域模型或
被描述成产品已交付。

## 破坏性模式

遇到以下情况时停止扩张并暴露冲突：

- 用已经写出的代码反向定义用户需求；
- 把技术风险逐个建设成正式模块、页面或审批流程；
- 用表、接口、菜单、测试数量代替产品闭环；
- 把 fixture、SHADOW 或局部浏览器验证描述成真实业务完成；
- 未确认的新规则、对象或状态被写入正式 PRD；
- 为每个后端阶段复制一个用户页面；
- PRD、OpenSpec、路线图和运行行为互相矛盾却继续开发。

发现这些情况时，输出冲突、影响范围和待决事项。只允许继续不依赖该决策的调查、
原型和可逆验证。

## 与后续工作的关系

- PRD 决定产品范围和用户行为；
- UI/UX 设计细化信息架构、交互和视觉基线；
- OpenSpec/SDD 定义跨模块或跨项目的目标行为与技术边界；
- 任务计划定义顺序、ownership 和验证；
- 测试与 E2E 证明实现符合已确认基线；
- `post-dev-prd-sync` 只同步已批准且已交付的行为变化，发现规格漂移时返回待决，
  不替代码改写产品意图。
