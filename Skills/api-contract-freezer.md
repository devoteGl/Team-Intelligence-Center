# API Contract Freezer（接口契约冻结技能）

## 技能用途
- 服务角色：**PM (Tech Lead / PM)**
- 触发时机：CI 调研完成，PM 方案制定后，FE/BE 并行实现阶段开始前
- 输出物：已冻结的接口契约文档
- 适用场景：前后端需要并行开发的任何需求迭代

> 对应 `coding-rules.md` 第 2 节：
> "FE/BE 并行开始前，PM 必须先冻结 `types/` 接口契约，双方基于已冻结契约各自实现，不得在并行期间修改共享类型定义。"

---

## 0. 核心原则

> 契约冻结的本质是**在并行开发开始前，锁定前后端之间的数据交换协议**。
> 冻结后的契约是 FE 和 BE 各自独立工作的唯一依据，任何修改都必须通过 PM 仲裁。

**绝对禁止**：
- FE/BE 在并行期间私自修改已冻结的契约
- 契约中存在模糊定义（如："返回相关数据"、"包含必要字段"）
- 跳过契约冻结直接进入并行开发
- 契约冻结后不通知相关方

---

## 1. 契约冻结触发条件（Pre-freeze Checklist）

在执行冻结前，PM 必须确认以下前置条件全部满足：

```markdown
## 冻结前检查清单

- [ ] CI 调研报告已提交且通过 CP-2
- [ ] PM 已明确本次需求涉及的所有功能点（F-XXX）
- [ ] PM 已明确哪些功能点需要前后端协作（非纯前端/纯后端）
- [ ] 数据需求（D-XXX）已定义（来源于 PRD 或调研报告）
- [ ] 核心业务规则（R-XXX）已确认（至少 S1/S2 级别）
```

全部通过后，进入契约定义阶段。

---

## 2. 接口契约定义协议（Contract Definition Protocol）

### 2.1 契约覆盖范围

每个需要前后端协作的功能点（F-XXX），至少定义一个接口契约。每个契约必须包含以下信息：

| 字段 | 必填 | 说明 |
|------|------|------|
| 契约编号 | ✅ | 格式：`C-XXX`，全局唯一递增 |
| 关联功能点 | ✅ | 对应的 F-XXX 编号 |
| 关联数据需求 | ✅ | 对应的 D-XXX 编号 |
| 接口名称 | ✅ | 语义化命名，如"获取活动列表" |
| 请求方向 | ✅ | `FE → BE`（读取/写入）或 `BE → FE`（推送） |
| 请求参数 | ✅ | 完整字段定义（名称、类型、必填、约束） |
| 响应结构 | ✅ | 完整字段定义（名称、类型、说明） |
| 错误码 | ✅ | 该接口可能返回的业务错误码 |
| 分页规则 | 按需 | 列表接口必填（每页条数、排序规则） |
| 关联业务规则 | 按需 | 该接口承载的 R-XXX 规则 |

### 2.2 契约定义模板

```markdown
### C-001: 获取活动列表

- **关联功能点**：F-001
- **关联数据需求**：D-001
- **请求方向**：FE → BE（读取）

#### 请求参数

| 字段 | 类型 | 必填 | 说明 | 约束 |
|------|------|------|------|------|
| page | number | 是 | 页码 | ≥ 1 |
| pageSize | number | 是 | 每页条数 | 默认 20，最大 100 |
| status | number | 否 | 状态筛选 | 枚举值见状态定义 |
| startDate | string | 否 | 开始日期 | 格式：YYYY-MM-DD |
| endDate | string | 否 | 结束日期 | 格式：YYYY-MM-DD，≥ startDate |

#### 响应结构

| 字段 | 类型 | 说明 |
|------|------|------|
| total | number | 总记录数 |
| list | Array\<Activity\> | 活动列表 |
| list[].id | number | 活动 ID |
| list[].name | string | 活动名称 |
| list[].startTime | string | 开始时间（ISO 8601） |
| list[].endTime | string | 结束时间（ISO 8601） |
| list[].status | number | 状态（0=草稿, 1=已发布, 2=已结束） |
| list[].participantCount | number | 当前参与人数 |
| list[].participantLimit | number | 人数上限（0=不限） |

#### 错误码

| 错误码 | 含义 | 触发条件 |
|--------|------|---------|
| 400 | 参数校验失败 | startDate > endDate |
| 401 | 未登录 | Token 无效或过期 |

#### 关联业务规则
- R-001: 活动列表默认按创建时间倒序
```

### 2.3 数据类型定义模板

如果契约中涉及复杂数据结构（如枚举、嵌套对象），必须集中定义：

```typescript
// ========= 冻结类型定义 =========
// 冻结版本：v1.0
// 冻结日期：YYYY-MM-DD
// 冻结人：PM

/** 活动状态枚举 */
enum ActivityStatus {
  DRAFT = 0,       // 草稿
  PUBLISHED = 1,   // 已发布
  ENDED = 2,       // 已结束
  CANCELLED = 3,   // 已取消
}

/** 活动实体 */
interface Activity {
  id: number;
  name: string;
  startTime: string;        // ISO 8601
  endTime: string;          // ISO 8601
  status: ActivityStatus;
  participantCount: number;
  participantLimit: number;  // 0 = 不限
}

/** 分页响应通用结构 */
interface PageResponse<T> {
  total: number;
  list: T[];
}
```

## 3. 契约冻结操作（Freeze Protocol）

### 3.1 冻结声明格式

当所有契约定义完成、PM 确认无误后，正式发布冻结声明：

```markdown
---
🔒 契约冻结声明

冻结版本：v1.0
冻结日期：YYYY-MM-DD
冻结人：PM
冻结范围：C-001 ~ C-005（共 5 个接口契约）

关联功能点：F-001, F-002, F-003
关联数据需求：D-001 ~ D-005

FE 负责人确认：⏸️ 等待确认
BE 负责人确认：⏸️ 等待确认

生效条件：FE/BE 双方确认后生效，进入并行开发阶段
---
```

### 3.2 冻结生效的检查点

契约冻结声明发布后，必须触发 **CP-3 检查点**（`coding-rules.md` 第 5 节）：

> ✅ CP-3 | 并行阶段开始前 | 用户确认接口契约已冻结

**只有用户（Product Owner）明确确认后**，FE/BE 才可各自开始独立开发。

## 4. 契约变更管理（Post-freeze Change Control）

### 4.1 变更申请流程

冻结后若需修改契约，必须严格遵循以下流程：

```text
Step 1 → 需修改方（FE 或 BE）向 PM 提出变更申请
Step 2 → PM 评估影响范围（影响哪些 C-XXX、F-XXX、对方的工作量）
Step 3 → PM 在当前会话中给出仲裁结论
Step 4 → 仲裁结论记录在 SESSION SNAPSHOT 中
Step 5 → 通知对方接受变更，更新契约版本号
```

### 4.2 变更申请格式

```markdown
📝 契约变更申请

申请方：FE / BE
契约编号：C-003
变更类型：[新增字段 / 修改类型 / 删除字段 / 新增接口]

变更描述：
- C-003 响应中需新增 `creatorName` 字段（string 类型），用于列表页展示创建人

变更原因：
- PRD §4.2 页面交互说明中要求展示创建人，但原始契约遗漏

影响评估（申请方自评）：
- FE 影响：列表组件增加一列展示，工作量约 0.5h
- BE 影响：[待对方评估]
```

### 4.3 契约版本号递增规则

| 变更类型 | 版本号变化 | 示例 |
|---------|----------|------|
| 新增可选字段 | 次版本号 +1 | v1.0 → v1.1 |
| 修改字段类型/约束 | 主版本号 +1 | v1.1 → v2.0 |
| 删除字段 | 主版本号 +1 | v1.1 → v2.0 |
| 新增接口 | 次版本号 +1 | v1.1 → v1.2 |
| 删除接口 | 主版本号 +1 | v1.2 → v2.0 |

## 5. 契约文档存放与命名

### 5.1 文件存放位置

契约文档应存放在项目的共享类型目录中（对应 `coding-rules.md` 第 3 节的共享文件域）：

```text
推荐路径：
├── types/                          # 共享类型目录（需 PM 仲裁才能修改）
│   ├── contracts/                  # 契约文档目录
│   │   ├── v1.0-活动管理.md        # 按功能域组织的契约文档
│   │   ├── v1.0-订单管理.md
│   │   └── shared-types.ts         # 共享类型定义文件
│   └── ...
```

### 5.2 契约文档在 SESSION SNAPSHOT 中的记录

每次冻结契约后，必须在 SESSION SNAPSHOT 中体现：

```text
冻结契约: types/contracts/v1.0-活动管理.md（已冻结，版本: v1.0，含 C-001~C-005）
```

## 6. 与上下游的衔接

### 上游：CI → PM → 契约冻结
- CI 报告中的**数据需求（D-XXX）和候选业务规则（CR-XXX）**是契约定义的输入
- PM 基于 CI 报告和 PRD，确定每个功能点需要哪些接口

### 下游：契约冻结 → FE/BE 并行
- FE 基于契约中的**响应结构**构建页面和 Mock 数据
- BE 基于契约中的**请求参数 + 业务规则 + 错误码**实现接口逻辑
- 双方独立开发，互不干扰，完成后在 QA 阶段集成验证
