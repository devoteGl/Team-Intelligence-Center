# Changelog Writer（双层变更日志编写技能）

## 技能用途
- 服务角色：**DS (Doc Specialist)**
- 触发时机：QA 验收通过后，DS 进入文档归档阶段
- 输出物：符合 `ai-prd-editor.rules.md` 强制模板的双层 Changelog
- 适用场景：任何版本发布、功能交付后的变更记录归档

> 对应 `ai-prd-editor.rules.md` 第 11 节：
> "全局和局部的 Changelog 都必须 100% 遵守以下结构模板，严禁擅自增删一级/二级标题。"

---

## 0. 核心原则

> Changelog 是项目的历史记忆。写得准不准，决定了后来者能否理解"为什么系统是现在这个样子"。
> DS 的使命是**忠实记录发生了什么**，而非评价做得好不好。

**绝对禁止**：
- 擅自增删模板中的一级/二级标题
- 将代码级文件变更细节写进全局总纲 `CHANGELOG.md`
- 将业务功能概述写进版本详情 `{版本号}/changelog.md`（那是总纲的职责）
- 遗漏任何已完成的功能点或文件变更
- 美化或弱化任何历史妥协与技术债务

---

## 1. 双层 Changelog 架构说明

```text
PRD/
├── CHANGELOG.md                    ← 第一层：全局总纲（What happened）
│                                      记录版本时间线 + 核心 Feature 列表
│                                      严禁包含代码文件变动细节
│
└── {版本号}/                        ← 第二层：版本详情（How it happened）
    └── changelog.md                   记录具体文件变更 + 技术实现细节
                                       用于研发验收与历史溯源
```

### 两层的边界

| 维度 | 全局总纲 `CHANGELOG.md` | 版本详情 `{版本号}/changelog.md` |
|------|----------------------|-------------------------------|
| **回答的问题** | 这个版本做了什么？ | 这个版本怎么做的？改了哪些文件？ |
| **读者** | PM、新人、任何需要了解项目历史的人 | 开发人员、QA、需要复查代码的人 |
| **粒度** | Feature 级别 | 文件 / 函数级别 |
| **包含代码细节？** | ❌ 绝对不包含 | ✅ 必须包含 |
| **长度参考** | 每个版本 3~8 行 | 每个版本 20~100+ 行 |

## 2. 第一层：全局总纲编写规范

### 2.1 强制模板

```markdown
# 项目变更日志 (Project Changelog)

## 0. 元信息
- **文档状态**：Active
- **最新版本**：{版本号}
- **更新时间**：{日期}

## 1. 版本历史

### v{版本号} ({日期})
[详情查阅](./{版本号}/changelog.md)
**[Feature] {功能域} - {功能标题}**
- **新增**：{一句话描述新增了什么}
- **修改**：{一句话描述修改了什么}
- **废弃**：{一句话描述废弃了什么}（如有）

### v{上一版本号} ({日期})
[详情查阅](./{上一版本号}/changelog.md)
**[Feature] {功能域} - {功能标题}**
- **新增**：...
```

### 2.2 编写规则

1. **版本按时间倒序排列**：最新版本在最前面
2. **每个版本必须有 `[详情查阅]` 链接**：指向版本详情 changelog
3. **变更动作仅限以下枚举**：`新增` / `修改` / `废弃` / `修复`
4. **每条描述不超过一句话**：如需详细说明，读者应跳转到版本详情
5. **Feature 标签必填**：格式为 `[Feature]`、`[Fix]`、`[Refactor]`、`[Chore]`
6. **禁止出现文件名**：如 `修改了 order.vue` 这类描述属于版本详情层级

### 2.3 示例

```markdown
### v4.4.340 (2026-03-11)
[详情查阅](./4.4.340/changelog.md)
**[Feature] 站点管理 - iOS/Android 应用配置拆分**
- **新增**：轮播图和快捷入口支持按 iOS/Android 独立配置
- **修改**：应用场景枚举新增 iOS 和 Android 独立选项

### v4.4.321 (2026-02-27)
[详情查阅](./4.4.321/changelog.md)
**[Feature] 落地训 - 实战班特价与购买资格**
- **新增**：支持实战班专属价格体系
- **修改**：购买前的资格前置校验逻辑重构
```

## 3. 第二层：版本详情编写规范

### 3.1 强制模板

```markdown
# {版本号} 变更日志

## 概述
- {用一两句话概括此版本做了什么}

## 文件变更清单
| 文件 | 变更类型 | 说明 |
|------|----------|------|
| {文件路径} | 新增/修改/删除 | {一句话说明} |

## 详细变更

### 日期: {YYYY-MM-DD}

#### {文件名} ({变更类型})
- {具体改了什么，逻辑层面描述}
- {如涉及 UI 交互变化，描述操作与响应}
- {如涉及业务规则变化，引用 R-XXX 编号}
```

### 3.2 编写规则

1. **概述必须精炼**：不超过 3 个要点
2. **文件变更清单必须完整**：所有被本次版本改动过的文件都必须列出
3. **变更类型仅限枚举**：`新增` / `修改` / `删除` / `重命名`
4. **详细变更按日期分组**：如果版本开发跨越多天，按天组织
5. **每个文件的变更，必须描述"改了什么逻辑"**：禁止只写 "优化代码" 这样的空话
6. **涉及业务规则变化时，引用 R-XXX 编号**：确保可追溯到 `main-prd.md`
7. **涉及历史决策或妥协时，必须记录原因**：后来者需要理解"为什么这么做"

### 3.3 示例

```markdown
# 4.4.340 变更日志

## 概述
- 轮播图和快捷入口支持按 iOS/Android 独立配置
- 应用场景枚举新增 iOS 和 Android 独立选项

## 文件变更清单
| 文件 | 变更类型 | 说明 |
|------|----------|------|
| src/views/siteManager/carouselList/add.vue | 修改 | 应用场景选择器支持 iOS/Android 拆分 |
| src/views/siteManager/districtSetting/add.vue | 修改 | 快捷入口配置支持 iOS/Android 拆分 |
| server/controller/SlideManagerController.java | 修改 | 轮播图查询接口增加应用类型筛选 |
| server/controller/QuickLinkController.java | 修改 | 快捷入口查询接口增加应用类型筛选 |

## 详细变更

### 日期: 2026-03-11

#### carouselList/add.vue (修改)
- 应用场景下拉选项从 [全部, App] 扩展为 [全部, App, iOS, Android]
- 选择 iOS 或 Android 后，该轮播图仅在对应平台展示
- 历史数据兼容：原有 "App" 选项数据自动作为"全部"处理

#### SlideManagerController.java (修改)
- 查询接口新增 `appType` 参数（可选，枚举值：ALL/IOS/ANDROID）
- 未传 appType 时返回全部数据（向后兼容）
- 关联业务规则：R-015（iOS 审核合规要求独立内容管控）
```

## 4. 执行流程（DS Workflow）

### Step 1: 收集变更信息

DS 需要从以下来源收集变更信息：

| 信息来源 | 获取方式 | 获取内容 |
|---------|---------|---------|
| Git 提交记录 | `git log --oneline` | 本版本所有 commit 的概要 |
| Git 文件差异 | `git diff` | 实际修改了哪些文件 |
| PRD / 需求文档 | 阅读 `req.md` | 本版本的功能需求描述 |
| QA 验收报告 | 阅读测试报告 | 实际验证通过的功能点 |
| PM 任务清单 | 阅读 SESSION SNAPSHOT | 任务拆解和完成状态 |

### Step 2: 填充版本详情

按 **第 3 节模板** 填写 `PRD/{版本号}/changelog.md`

### Step 3: 更新全局总纲

按 **第 2 节模板** 在 `PRD/CHANGELOG.md` 顶部追加新版本条目

### Step 4: 自检

执行以下检查：

```markdown
## Changelog 自检清单

### 结构检查
- [ ] 全局总纲的一级/二级标题是否与模板完全一致？
- [ ] 版本详情的一级/二级标题是否与模板完全一致？
- [ ] 全局总纲中是否包含了"详情查阅"链接？

### 内容检查
- [ ] 所有被修改的文件是否都列入了文件变更清单？
- [ ] 每个文件的变更描述是否说明了"改了什么逻辑"（而非 "优化代码"）？
- [ ] 涉及业务规则变化的条目是否引用了 R-XXX 编号？

### 边界检查
- [ ] 全局总纲中是否误包含了文件名或代码细节？
- [ ] 版本详情中是否遗漏了业务决策的原因说明？
- [ ] 版本号和日期是否准确？

### 一致性检查
- [ ] 全局总纲中的功能描述与版本详情是否一致（不矛盾）？
- [ ] 版本详情中的文件列表与实际 Git 变更是否一致？
```

## 5. 特殊场景处理

### 5.1 版本交叉修改

当一个版本的改动修改了上一版本引入的功能时：

```markdown
#### orderDetail.vue (修改)
- 修复 v4.4.321 引入的退款按钮状态判断逻辑
- 原逻辑：仅判断 order.status === 'PAID'
- 修正后：增加判断 order.refundStatus !== 'PROCESSING'
- [继承自 v4.4.321 changelog, 章节: 退款功能]
```

### 5.2 回滚操作

当版本包含对历史功能的回滚时：

```markdown
#### gravityField.js (回滚)
- 回滚 v4.4.330 引入的衰减算法至 v4.4.325 版本逻辑
- 回滚原因：新算法在边界条件下出现数值溢出（Issue #247）
- 影响范围：所有使用反重力场计算的模块
```

### 5.3 纯重构（无功能变更）

```markdown
### v4.4.335 (2026-03-01)
[详情查阅](./4.4.335/changelog.md)
**[Refactor] 订单模块 - 组件拆分与状态管理优化**
- **修改**：orderDetail.vue 拆分为 5 个子组件，消除状态耦合
```

## 6. 与上下游的衔接

### 上游：QA → DS
- QA 验收通过后，将验收报告和通过的功能点清单交给 DS
- DS 基于验收结果 + Git 差异，编写 Changelog

### 下游：DS → main-prd.md 同步
- 当版本 changelog 中包含业务规则变更时，DS 必须提醒 PM：
  - 是否需要将新规则同步至 `main-prd.md`
  - 是否有候选规则（CR-XXX）需要转正
  - 是否有旧规则需要标记 `deprecate`

> 参照 `ai-prd-editor.rules.md` 第 12 节：
> "每次版本发布后，必须将新版本的逻辑抽象合并到 main-prd.md 中，替换并淘汰旧逻辑。"
