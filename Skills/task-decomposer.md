# Task Decomposer（任务拆解技能）

## 技能用途
- 服务角色：**PM (Tech Lead / PM)**
- 触发时机：任何新任务开始时，PM 执行任务拆解
- 输出物：结构化任务清单（含优先级、依赖关系、阻塞链、负责角色）
- 适用场景：新需求开发、Bug 修复、技术重构、文档补全等所有类型的任务

> 对应 `coding-rules.md` 第 2 节：
> "PM 必须在响应开始时输出任务清单。"

---

## 0. 核心原则

> 任务拆解的目标是**让每个角色都清楚：我要做什么、我依赖谁、谁在等我**。
> 拆解粒度以「一个角色在一个阶段内可独立完成」为标准。

**绝对禁止**：
- 拆出无法验收的任务（如"优化代码"——验收标准是什么？）
- 遗漏任务间的依赖关系
- 将 FE 和 BE 的工作混在同一个任务中
- 未标注优先级就发布任务清单

---

## 1. 拆解维度（Decomposition Axes）

### 1.1 按工作流阶段拆解

每个需求至少包含以下阶段性任务：

```text
调研任务（CI）→ 设计任务（PM）→ 实现任务（FE/BE）→ 测试任务（QA）→ 文档任务（DS）
```

### 1.2 按角色职责拆解

| 角色 | 典型任务类型 | 输出物 |
|------|------------|--------|
| CI | 调研现有代码/模块/接口 | 现状报告 |
| PM | 方案设计、契约冻结、任务分配 | 方案文档、契约文件 |
| FE | 页面开发、组件开发、交互实现 | 前端代码 |
| BE | 接口开发、业务逻辑、数据库设计 | 后端代码 |
| QA | 功能测试、边界测试、回归测试 | 测试报告 |
| DS | 文档编写、changelog 更新 | 文档文件 |

### 1.3 按功能模块拆解

对于涉及多个功能模块的需求，每个模块应独立拆出任务：

```text
需求：实现用户管理系统
├── 模块A：用户列表
│   ├── FE-001: 实现用户列表页面
│   └── BE-001: 提供用户列表接口
├── 模块B：用户详情
│   ├── FE-002: 实现用户详情页面
│   └── BE-002: 提供用户详情接口
└── 模块C：用户权限
    ├── FE-003: 实现权限配置页面
    └── BE-003: 实现权限校验逻辑
```

## 2. 任务清单输出格式

### 2.1 标准格式

```text
📋 TASKS
[🔴高] #1 {任务描述} → 负责人: {角色} | 状态: {状态} | 阻塞: #{被阻塞的任务编号}
[🟡中] #2 {任务描述} → 负责人: {角色} | 状态: {状态} | 依赖: #{依赖的任务编号}
[🟢低] #3 {任务描述} → 负责人: {角色} | 状态: {状态} | 依赖: #{依赖的任务编号}
```

### 2.2 优先级定义

| 标记 | 级别 | 含义 | 判定标准 |
|------|------|------|---------|
| 🔴 | 高 | 阻塞其他任务或影响核心功能 | 不完成此任务，后续任务无法开始 |
| 🟡 | 中 | 影响功能完整性或用户体验 | 可独立完成，但延迟会影响整体交付 |
| 🟢 | 低 | 锦上添花或可后续迭代 | 不影响核心功能交付 |

### 2.3 依赖关系标注

| 标注 | 含义 | 示例 |
|------|------|------|
| `依赖: #1` | 需要 #1 完成后才能开始 | BE 任务依赖 CI 调研结果 |
| `阻塞: #2, #3` | #2 和 #3 在等待本任务完成 | CI 调研阻塞了 FE/BE 实现 |
| `并行: #2` | 可与 #2 同时进行 | FE 和 BE 可并行（契约冻结后） |

### 2.4 状态枚举

| 状态 | 含义 |
|------|------|
| 未开始 | 尚未启动 |
| 进行中 | 当前正在执行 |
| 已完成 | 已交付并验收 |
| 已驳回 | QA 驳回，需返工 |
| 阻塞中 | 被依赖项未完成而阻塞 |

## 3. 拆解质量自检

PM 在输出任务清单前，必须执行以下自检：

```markdown
## 任务拆解自检清单

### 完整性
- [ ] 是否覆盖了从调研到文档的完整工作流？
- [ ] 每个需要前后端协作的功能是否同时有 FE 和 BE 任务？
- [ ] 是否有 QA 验收任务？
- [ ] 是否有 DS 文档归档任务？

### 粒度
- [ ] 每个任务是否可被单一角色独立完成？
- [ ] 每个任务是否有明确的交付物？
- [ ] 是否存在过大的任务需要进一步拆分？（建议单任务工时不超过 1 天）

### 依赖关系
- [ ] 所有任务的依赖关系是否标注完整？
- [ ] 是否存在循环依赖？（绝对禁止）
- [ ] 可并行的任务是否标注了并行关系？

### 可验收
- [ ] 每个任务的完成标准是否清晰？
- [ ] PM 能否判断"这个任务做完了"？
```

## 4. 任务拆解示例

### 示例：实现活动管理功能

```text
📋 TASKS
[🔴高] #1 调研现有活动相关代码与数据结构 → 负责人: CI | 状态: 未开始 | 阻塞: #2, #3, #4
[🔴高] #2 制定活动管理技术方案与接口契约 → 负责人: PM | 状态: 未开始 | 依赖: #1 | 阻塞: #3, #4
[🔴高] #3 实现活动列表/创建/详情页面      → 负责人: FE | 状态: 未开始 | 依赖: #2 | 并行: #4
[🔴高] #4 实现活动 CRUD 接口与业务规则    → 负责人: BE | 状态: 未开始 | 依赖: #2 | 并行: #3
[🟡中] #5 实现活动状态流转逻辑            → 负责人: BE | 状态: 未开始 | 依赖: #4
[🟡中] #6 功能测试与边界验收              → 负责人: QA | 状态: 未开始 | 依赖: #3, #4, #5
[🟢低] #7 更新 CHANGELOG 与相关文档       → 负责人: DS | 状态: 未开始 | 依赖: #6
```

## 5. 与上下游的衔接

### 上游：用户需求 → PM 拆解
- 用户提出需求后，PM 优先产出任务清单
- 任务清单是 CP-1 检查点的审批对象

### 下游：PM 拆解 → 各角色执行
- 任务清单发布后，按依赖关系依次流转到各角色
- 每个角色只需关注分配给自己的任务
- 任务状态变更后，PM 负责在 SESSION SNAPSHOT 中同步更新
