# Conflict Arbiter（共享文件冲突仲裁技能）

## 技能用途
- 服务角色：**PM (Tech Lead / PM)**
- 触发时机：FE 或 BE 需要修改共享文件域中的文件时
- 输出物：仲裁结论（含影响范围评估与修改授权）
- 适用场景：并行开发阶段对 `router/`、`types/`、`constants/` 等共享文件的修改请求

> 对应 `coding-rules.md` 第 3 节：
> "FE 和 BE 不得修改对方的文件域，并行工作时必须声明文件所有权。"
> "共享文件（需 PM 仲裁才能修改）：router/, types/, constants/"

---

## 0. 核心原则

> 共享文件是 FE/BE 的公共边界。任何修改都可能同时影响双方。
> PM 作为仲裁者，必须评估每次修改对双方的影响，避免并行期间的代码冲突。

**绝对禁止**：
- FE/BE 不经仲裁直接修改共享文件
- PM 不评估影响范围就直接授权
- 仲裁结论不记入 SESSION SNAPSHOT

---

## 1. 文件域定义（Domain Boundaries）

### 1.1 独占文件域

| 角色 | 文件域 | 规则 |
|------|--------|------|
| FE | `src/components/`, `src/views/`, `src/styles/`, `*.vue`, `*.css` | FE 独占，BE 不得修改 |
| BE | `src/api/`, `src/store/`, `server/`, `*.ts`（纯逻辑） | BE 独占，FE 不得修改 |

### 1.2 共享文件域（需仲裁）

| 目录 | 内容类型 | 典型修改场景 |
|------|---------|-------------|
| `router/` | 路由配置 | 新增页面路由、修改路由守卫 |
| `types/` | TypeScript 类型定义 | 新增/修改接口契约、共享类型 |
| `constants/` | 常量定义 | 新增/修改枚举值、配置常量 |

---

## 2. 仲裁申请流程

### 2.1 申请触发条件

当 FE 或 BE 在开发过程中发现需要修改共享文件域中的文件时，必须向 PM 提交仲裁申请。

### 2.2 申请格式

```markdown
📝 共享文件修改申请

申请方：FE / BE
申请时间：YYYY-MM-DD

### 修改对象
- 文件路径：{共享文件域中的具体文件}
- 修改类型：[新增文件 / 新增内容 / 修改内容 / 删除内容]

### 修改内容
- 具体要改什么（diff 预览或描述）

### 修改原因
- 为什么需要修改这个共享文件
- 关联的任务编号：#{任务编号}
- 关联的功能点：F-{XXX}

### 影响评估（申请方自评）
- 对本方的影响：{描述}
- 对对方的影响：{描述，或"无影响"并说明原因}
```

### 2.3 申请示例

```markdown
📝 共享文件修改申请

申请方：BE
申请时间：2026-03-18

### 修改对象
- 文件路径：constants/orderStatus.js
- 修改类型：新增内容

### 修改内容
- 新增枚举值 `REFUND_PROCESSING = 5`（退款处理中）

### 修改原因
- 退款功能需要新增中间状态以支持异步退款流程
- 关联任务编号：#4
- 关联功能点：F-005

### 影响评估（申请方自评）
- 对 BE 的影响：退款接口新增状态判断逻辑
- 对 FE 的影响：订单列表页状态标签需新增"退款处理中"文案映射
```

## 3. PM 仲裁流程

### 3.1 评估清单

PM 收到申请后，必须评估以下维度：

```markdown
## 仲裁评估

### 1. 合理性评估
- [ ] 修改理由是否充分？
- [ ] 是否确实需要修改共享文件？（能否通过修改独占域文件来解决？）

### 2. 影响范围评估
- [ ] 申请方自评的影响范围是否准确？
- [ ] 对方是否受影响？影响程度如何？
- [ ] 是否影响已冻结的接口契约？（若是，需走契约变更流程）

### 3. 冲突风险评估
- [ ] 是否与对方正在进行的工作存在代码冲突？
- [ ] 修改时机是否合适？（是否应该等对方完成某个任务后再修改？）

### 4. 向后兼容评估
- [ ] 修改是否向后兼容？（新增 vs 修改已有内容）
- [ ] 是否需要对方同步修改代码？
```

### 3.2 仲裁结论格式

```markdown
⚖️ 仲裁结论

**申请编号**：ARB-{XXX}
**申请方**：{FE/BE}
**仲裁时间**：YYYY-MM-DD
**仲裁结果**：✅ 批准 / ❌ 驳回 / ⚠️ 有条件批准

### 结论说明
{说明批准/驳回的原因}

### 影响通知
- 对方（{FE/BE}）需要：{具体的同步操作，或"无需操作"}
- 时间要求：{立即 / 在完成 #X 任务后 / 下一版本}

### 约束条件（如有条件批准）
- {列出限制条件}
```

### 3.3 仲裁结论示例

```markdown
⚖️ 仲裁结论

**申请编号**：ARB-001
**申请方**：BE
**仲裁时间**：2026-03-18
**仲裁结果**：⚠️ 有条件批准

### 结论说明
批准新增 `REFUND_PROCESSING = 5` 枚举值。但由于此变更影响 FE 的状态标签渲染，需通知 FE 同步更新。

### 影响通知
- FE 需要：在订单列表页的状态标签映射中新增 `5 → "退款处理中"` 的文案
- 时间要求：FE 在完成 #3 任务后同步更新

### 约束条件
- BE 仅可新增枚举值，不得修改已有枚举值的数值
- 新增的枚举值必须附带注释说明
```

## 4. 仲裁记录管理

### 4.1 记录存储

所有仲裁结论必须记录在当次会话的 SESSION SNAPSHOT 中：

```text
仲裁记录:
  ARB-001: BE 新增 orderStatus 枚举值 REFUND_PROCESSING=5（已批准，FE 需同步）
  ARB-002: FE 新增路由 /order/refund（已批准，无影响）
```

### 4.2 回溯追踪

当未来出现代码冲突或逻辑矛盾时，可通过仲裁编号（ARB-XXX）回溯当时的决策过程。

---

## 5. 特殊场景处理

### 5.1 紧急修改（Hotfix）

在紧急 Bug 修复场景下，允许简化仲裁流程：

```text
紧急流程：
1. 修改方在代码注释中标注 `// HOTFIX: 待仲裁 ARB-XXX`
2. 修复完成后，补提仲裁申请
3. PM 事后补录仲裁结论
```

### 5.2 双方同时需要修改同一文件

```text
处理流程：
1. PM 评估双方修改是否冲突
2. 若不冲突 → 指定先后顺序（通常先改的一方负责通知后改的一方）
3. 若冲突 → PM 设计合并方案，由一方统一执行修改
```

### 5.3 删除共享文件

删除共享文件属于高风险操作，必须同时触发 **CP-4 检查点**（用户明确授权）。

---

## 6. 与上下游的衔接

### 上游：FE/BE → PM
- 开发过程中发现需要修改共享文件时，向 PM 提交仲裁申请
- 申请必须包含影响自评

### 下游：PM → FE/BE
- PM 发布仲裁结论后，受影响方按结论执行同步操作
- 仲裁结论记入 SESSION SNAPSHOT
