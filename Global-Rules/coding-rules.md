# Git 规则入口

Git 分支、commit message、长期分支保护、版本、tag、回灌和 submodule 顺序以
`Global-Rules/git-rules.md` 为唯一事实源。本文件只维护通用工程边界，不复制
第二套 Git 命名规范。

---

# AI Agent Working Rules

## 0. Workflow 事实源

TIC 的默认工作方式以 `Workflow/core.md` 为唯一决策事实源。能力 metadata
以 `Workflow/capability-schema.md` 为准。

核心行为：

- 普通任务直接调查、修改和验证。
- 规划深度、执行授权、验证范围、Review 和事实持久化分别判断。
- 只在产品方向无法从事实确定或准备执行受保护动作时暂停。
- 普通任务不调用 Orchestrator 或总控型外部 Skill。
- 额外产物必须存在明确消费者或后续用途。
- 普通任务不因 OpenSpec 存在而强制创建 change。
- 风险只保护产生风险的具体动作和必要范围。

本文件补充工程行为边界，不复制完整 workflow，也不维护第二套分级模型。

## 1. 开始工作

开始时理解：

```yaml
outcome: 用户要得到的结果
boundaries: 不允许触碰的范围和副作用
done: 全部验收标准
verification: 能证明完成的新鲜证据
authority: Agent 可以自主执行和必须确认的动作
```

信息不足时：

1. 能从项目文件、代码、运行时或只读工具确认的，先调查。
2. 影响小且容易回滚的，采用合理假设并在交付时说明。
3. 会产生明显不同产品结果的选择，询问用户。
4. 受保护动作必须在执行前获得明确授权。

“全自动”“不用问我”“你看着办”允许范围内的可逆本地工作和非破坏性
验证，不授权生产、外部写入、数据删除、迁移、Git 状态变化、发布或正式
文档转正。

## 2. 项目事实

按以下优先顺序理解项目：

1. 用户当前指令和明确授权；
2. 当前项目 `AGENTS.md` 及更具体目录规则；
3. `ai-harness/project-adapter.md`；
4. 正式 OpenSpec、PRD、决策记录和契约；
5. 指定 ref 的代码、运行时、测试和数据；
6. 已确认且未过期的项目记忆；
7. 推断和候选规则。

不得编造业务事实。代码反推必须标注证据和可信度，未经确认不能写成正式
需求。不得覆盖用户未提交改动；发现工作区已有变化时，先区分当前任务和
他人工作。

`project-adapter.md` 是项目维护的事实与治理配置。普通安装和升级必须保留
现有非占位内容、自定义章节和本地决策。只有用户要求创建、补全、审计、
迁移或修复时才使用 `project-adapter-maintainer`。

## 3. Capability 选择

Capability 可以直接调用，不需要经过中心路由。先应用 `activation.not_when`；
只有用户明确要求、当前事实满足 `activation.when`，或缺少它会使任务无法
安全完成时才选择。技术关键词、文件类型、改动规模和任务完成状态不能单独
触发 Capability。

常见映射：

| 事实 | Capability |
| --- | --- |
| 代码现状、调用路径或影响面未知 | `code-investigator` |
| 用户要求计划，或无法安全地边调查边执行 | `task-decomposer` |
| 公共接口存在多个消费者 | `contract-handoff` |
| 多个执行者存在共享域 ownership 冲突 | `shared-domain-arbiter` |
| 协作跨任务、跨工具、长时异步或需要审计 | `agent-session-protocol` |
| 局部测试不足以证明关键旅程 | `e2e-verification` |
| Reviewer、QA、运营或使用方需要异步说明 | `delivery-walkthrough` |
| 产品事实变化且存在维护中的 PRD | `post-dev-prd-sync` |
| 准备形成版本发布记录 | `changelog-writer` |
| 真实进入部署或运营交接 | `release-handoff` |
| 用户要求协作记忆或确认经验值得复用 | `collaboration-memory-maintainer` |
| 用户明确要求 Git 生命周期操作 | `git-flow-operator` |

`related` 只用于发现，不授权调用。不得自动级联 Capability，也不得输出
未选择能力的全量跳过清单。

## 4. 用户确认边界

以下动作必须暂停确认：

| 动作 | 确认内容 |
| --- | --- |
| 重大产品方向选择 | 目标、范围或行为方向 |
| 删除或覆盖难恢复内容 | 精确目标、恢复方式、影响范围 |
| 生产或外部系统写入 | 环境、对象、副作用、停止条件 |
| 权限、安全、资金、隐私变化 | 边界、兼容、验证和责任人 |
| 数据库迁移 | 数据范围、备份、回滚和验证 |
| 分支、提交、推送、合并、tag | 目标、命令、基线和远端状态 |
| 发布或部署 | release owner、版本、顺序、回滚和观察 |
| 正式规格、规则或共享记忆转正 | 证据、确认人和事实源 |
| 失败补救扩域 | 新范围、新风险和授权 |

暂停只针对受保护动作。此前可安全完成的调查、方案、测试准备和局部验证应
继续推进。

用户在当前任务对具体受保护结果的明确要求，就是该结果的确认。远端、目标、
版本、覆盖行为和影响可唯一解析时不得重复询问；只有出现歧义、授权外扩或新
的高后果副作用时再次确认。

## 5. 实现与 ownership

- 修改前读取相关文件、调用路径和已有测试。
- 优先复用项目现有模式、命令和依赖。
- 修改范围保持与目标一致，不顺便重构无关代码。
- 单个执行者在授权范围内修改共享文件不需要额外仲裁。
- 多个执行者存在并发 ownership 或互斥修改时，使用
  `shared-domain-arbiter`。
- 多个消费者依赖公共契约时，先明确 `contract-handoff`。
- 子 Agent 不得获得超出父任务的授权；主 Agent 负责最终 diff 和验证。

同一任务内的原生 subagent 使用宿主线程和主 Agent 汇总。只有切换任务或
工具、跨人接力、长时异步或需要审计时，才使用会话 artifact。`session_id`
只用于追踪，不是事实源。

## 6. 验证

没有新鲜验证证据，不得声称完成或修复。

- 优先运行受影响范围内最相关、可重复的项目原生测试。
- 需要时再扩大到构建、lint、集成、E2E 或相邻回归。
- UI 改动在本地应用可运行时核对真实界面；工具可以是项目现有测试、
  Playwright、浏览器、Computer Use 或截图。
- E2E 只在局部测试不足以证明关键用户或系统旅程时启用。
- 认证状态必须保存在本地并 gitignored。
- 只清理本次验证拥有的数据。
- 生产账号、真实资金、真实通知和外部不可逆写入仍需明确授权。
- 无法完成理想验证时，报告替代证据、未测项和剩余风险。
- `partial`、`blocked` 和 `waived` 不得描述为通过。

项目已有 OpenSpec 时，它可以承载长期目标行为；执行计划、TDD、调试和
review 方法可以替换。普通任务不因 OpenSpec 存在而强制创建 change。

## 7. Memory

Memory 是显式能力，不默认进入每个任务的开始或收尾。

- 跨任务读取历史对话必须获得用户明确授权。
- 当前用户指令、代码、运行时和正式规格优先于历史记忆。
- 个人偏好和未确认候选保存在 gitignored 的 `.tic/local/`。
- 团队与项目资产保存在 `ai-harness/memory/` 前必须有证据和确认。
- 不保存原始聊天、思维链、密钥、cookie、认证状态、个人敏感信息或未脱敏
  生产数据。
- 安装和升级必须逐文件保留现有 memory，不得用模板覆盖。

## 8. Git 与发布

不默认执行分支、提交、推送、合并、tag 或发布。

用户明确要求 Git 生命周期操作时：

1. 读取 `Global-Rules/git-rules.md`、项目 adapter 和仓库实际 branch、version、
   tag 策略。
2. 分支创建前执行 `git fetch <authoritative-remote> --prune --tags`。
3. 检查基线新鲜度和本地/远端同名分支。
4. 核对目标、命令和风险；当前任务未授权或存在歧义时才等待确认。
5. 使用原生 Git 输出保留执行证据。
6. release/hotfix tag 后继续记录项目要求的回灌或收尾状态。

真实进入部署或运营交接时使用 `release-handoff`，按项目实际记录 owner、
部署方式、验证、回滚和观察；只有项目使用 registry 或 tag 时才记录相应
字段。创建发布材料不等于已经授权发布。

## 9. 产物与交付

任务摘要是默认交付。只有以下消费者存在时才创建额外文件：

- Reviewer / QA：Walkthrough 或验证证据；
- 产品维护者：PRD 更新草稿；
- 发布 / 运维人员：Changelog 或 Release Handoff；
- 后续协作者：已确认项目事实、决策或 runbook。

PRD 草稿、候选规则和 Memory 候选不得自动转正。

涉及修改时，最终报告包含：

- 得到的结果；
- 修改的文件或范围；
- 执行的验证及结果；
- 未验证内容和剩余风险；
- 尚未授权的受保护动作。

## 10. 可选工具

rtk 等输出压缩工具只改变 Agent 阅读输出的方式，不改变验证结论。

- 项目未显式启用时使用原生命令。
- Git 状态变更、发布、迁移、破坏性操作、生产命令和失败调试必须保留原始
  输出或可审计代理输出。
- 团队启用前应确认 telemetry 已关闭。
