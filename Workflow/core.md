# TIC Workflow Core

本文件是 TIC 工作方式的唯一决策事实源。它约束边界，不接管 Agent 的逐步
执行，也不维护必须经过的阶段、总控入口或 Skill 调用链。

## 1. 默认行为

普通任务直接调查、修改和验证。Agent 优先理解结果和边界，在授权范围内持续
推进；只有无法从事实消解的产品分歧或受保护动作才暂停。

最小任务契约包含五项：

| 字段 | 要回答的问题 |
| --- | --- |
| `outcome` | 用户最终要得到什么可观察结果？ |
| `boundaries` | 哪些范围、兼容性或副作用不能触碰？ |
| `done` | 哪些验收条件全部满足才算完成？ |
| `verification` | 用什么新鲜证据证明这些条件？ |
| `authority` | 哪些动作可自主执行，哪些必须确认？ |

任务契约默认存在当前任务上下文中，不要求用户填写模板，也不要求落盘。
能够从代码、文档、运行时或只读工具确认的信息先调查；低影响且容易回滚的
细节采用合理假设并在交付时说明。

### 1.1 产品基线门

普通任务仍直接执行。以下事实同时成立时，不得把任务当作普通实现：

- 从零建设产品、业务域或核心用户旅程；
- 目标、使用者、范围、主旅程或成功标准尚未形成已确认事实；
- 继续实现会通过 API、Schema、菜单、状态或领域模型冻结产品行为。

此时使用 `prd-author` 形成产品基线，并由有权 owner 决定重大产品方向。
确认产品基线前，可以继续调查、原型和可逆技术探针；不得让探针成为正式实现、
范围扩张或完成证据。该检查点保护产品决定，不恢复所有任务的阶段流水线。

用户可见产品还应在持久契约和正式实现前明确角色、主旅程、信息架构和关键状态。
视觉稿是否需要落盘由真实设计消费者决定；没有 UI 的产品不生成空设计产物。

## 2. 五个独立决策维度

这五个维度分别判断，不得用一个综合“任务等级”替代。

### 2.1 `planning_depth`

| 值 | 使用条件 |
| --- | --- |
| `inline` | 目标清楚，可以安全地边调查边执行 |
| `brief` | 多个消费者、公共契约或明显设计分歧需要简短对齐 |
| `living` | 长时、多里程碑、迁移或跨系统工作需要持续更新的计划 |

文件数、技术关键词和预计耗时不能单独决定规划深度。计划可以帮助执行，但不
自动产生用户检查点。

大型新产品、跨系统产品化或产品基线修复使用 `living`。计划至少在基线确认、
范围变化、里程碑完成、上下文压缩或用户要求继续后恢复当前状态；计划不能用
技术模块完成数替代产品旅程进度。

### 2.2 `execution_authority`

| 值 | 使用条件 |
| --- | --- |
| `autonomous` | 只读、本地可逆、非破坏性且在用户授权范围内 |
| `confirmation-required` | 当前准备执行的具体动作具有外部、不可逆或高后果副作用 |

以下动作需要确认：

- 难以恢复的数据、资源或历史删除和覆盖；
- 生产环境、真实用户状态或外部系统写入；
- 数据库迁移或高成本回滚；
- 权限、安全、资金或隐私边界变化；
- 创建分支、提交、推送、合并、tag 或正式发布；
- 将草稿转成正式规格、规则或共享记忆；
- 失败补救需要扩大原授权范围。

确认只保护具体动作；此前安全的调查、方案准备和本地验证继续完成。

### 2.3 `verification_scope`

| 值 | 证明对象 |
| --- | --- |
| `targeted` | 局部行为、静态检查或针对性回归 |
| `integration` | 模块、消费者、构建或跨层组合 |
| `e2e` | 关键用户旅程和真实交互 |
| `operational` | 迁移、部署、回滚、监控和运行态结果 |

验证不是收尾阶段，而是贯穿执行的证据线：

1. 开始时识别完成标准和证明方式；
2. 每个有独立行为的修改完成后就近验证；
3. 交付前重新运行能够证明用户结果的最终验证；
4. 无法执行理想验证时报告替代证据、未测项和剩余风险。

没有与完成标准直接对应的新鲜证据，不得声称完成或修复。

### 2.4 `review_level`

| 值 | 使用条件 |
| --- | --- |
| `self` | 普通修改完成后核对目标、完整 diff、边界和无关变化 |
| `independent` | 公共契约、跨项目、高后果、复杂实现或用户要求独立视角 |
| `user-decision` | 产品方向无法从事实判断，或受保护动作需要授权 |

Review 不是固定关卡。架构与公共契约在实现前 Review，代码在实现和相关验证
后 Review，生产与发布动作在执行前 Review。每个任务默认做轻量 diff 自审，
但不因此自动调用 Reviewer、subagent 或外部工具。

新产品基线从 `DRAFT` 转为 `CONFIRMED` 前使用 `user-decision`；PRD Review 只
判断基线是否可供实现，不批准代码、迁移或发布。

### 2.5 `fact_persistence`

| 值 | 使用条件 |
| --- | --- |
| `task-context` | 当前任务摘要足以支持交付 |
| `openspec` | 行为需要跨任务、跨项目或多人长期维护的规格契约 |
| `prd` | 产品维护者需要同步用户可见事实 |
| `runbook` | 运维或后续协作者需要可重复操作说明 |
| `release-record` | 真实进入发布、部署或运营交接 |
| `local-candidate` | 经验尚未确认，仅保存为 gitignored 候选 |

持久化必须有明确消费者。OpenSpec 是长期规格载体，不是任务入口；项目存在
`openspec/` 也不代表每个任务都要创建 change。同一事实只选择一个主事实源，
不得同时生成 OpenSpec、Superpowers spec 和重复 SDD。

大型新产品或重大用户旅程由产品 owner 长期消费时，产品基线使用 `prd`；跨实现
边界的稳定行为再选择 `openspec`。开发后的 PRD 同步不能创建初始产品基线，也
不能用实现结果覆盖未经批准的产品决定。

## 3. Capability 与外部方法

Capability 是按事实选择的方法库，不拥有任务控制权。选择时至少满足一项：

- 用户明确要求；
- 当前事实满足 capability 的 `activation.when`；
- 缺少该能力会使已授权任务无法安全或正确完成。

`related` 只用于发现，不授权调用；`requires` 只表达真正无法绕过的技术前置。
能力不得自动级联另一个能力，也不得扩大授权范围。

Codex 或其他宿主的原生调查、计划、调试、验证、Review、subagent 和 worktree
能力优先直接使用。Superpowers 等外部方法型 Skills 可以在具体方法确有增益时
选择，但总控型外部 Skill 不得成为项目默认入口，不得强制所有任务进入
brainstorm、计划、TDD、subagent、Review 或验证流水线。

## 4. 产物

当前任务摘要是默认交付。创建额外 artifact 前必须能回答：

1. 谁会使用；
2. 用它完成什么后续动作；
3. 为什么当前任务摘要不足；
4. 唯一主事实源和归档位置在哪里。

Memory 不默认进入任务开始或收尾。只有用户明确要求，或候选经验被确认具有
长期复用价值时，才检索、提取、晋升或审计。

## 5. 交付

普通交付说明：

- 得到的结果；
- 修改或调查的范围；
- 对应完成标准的验证及结果；
- diff Review 或独立 Review 的结论；
- 未验证内容、剩余风险和尚未授权的具体动作。

不得用流程名称代替事实，也不得把一个等待授权的动作描述成整个任务被阻塞。
